# P3 软件刷写

## Problem Statement

汽车嵌入式开发中，把编译产物刷进 ECU 是每天要做很多次的事。现在这件事只能靠厂商工具（Vector CANape / CANoe、ETAS INCA、各家的 bootloader 工具）完成，它们有几个共同的痛点：

1. **流程不可配置。** 不同 ECU、不同 Bootloader 的时序都不一样（进编程会话要不要等、安全访问的种子密钥算法、擦除是整片还是分段、传输块大小）。换一个 ECU 就要换一套工具或重写脚本。
2. **断了就得从头来。** 刷到 80% 断开连接，重跑一遍要重新擦写 Flash。十几分钟白等，而且反复擦写本身有风险。
3. **没有审计留痕。** 「谁在什么时间给哪台 ECU 刷了哪个版本的什么文件」这个问题，在体系审核时一定会被问到。临时日志不算数，它会被清理、会被覆盖。
4. **刷写过程和界面绑死。** 刷写跑十几分钟，界面崩溃、Python 异常、驱动挂掉都是常态，任何一方出问题都不该拖垮另一方。

本项目已经有 P0 骨架、P1 标定、P2 数据分析，缺的正是这一块：**在线、有状态、不可重放**的执行模式。

## Solution

把一次刷写拆成三个可独立替换的部分，用一个可序列化的通道边界隔开：

- **配方（Recipe）** 描述「按什么顺序做什么」——进编程会话、安全访问、擦除、传输、校验、复位。适配一个新 ECU = 加一个配方，不改主程序。
- **网关（Gateway）** 描述「怎么把字节送出去」——CAN / DoIP / 仿真。签名只传 `bytes`，因此它将来可以搬到独立进程甚至用 C++/Rust 重写。
- **编排（Job）** 负责进度汇报、断点续刷、审计留痕、不可取消步骤的保护。

三者只在一个地方碰面：**配方向网关发送字节、网关回字节**。这个边界就是唯一的测试缝（seam）。

关键取舍：**刷写逻辑本身不碰硬件、不碰进程、不碰界面**。它只看到「发出一串字节、收回一串字节」。这样整套刷写流程（包括断点续刷和审计）在没有 CAN 卡、没有 ECU 的机器上也能被完整验证。

## User Stories

1. 作为刷写工程师，我想要用一份配方文件描述某款 ECU 的刷写时序，以便换 ECU 时不用改主程序。
2. 作为刷写工程师，我想要配方是有序步骤的显式列表（而不是散落在代码里的 if/else），以便我能对照 Bootloader 手册逐条核对。
3. 作为刷写工程师，我想要每个步骤能单独声明超时与重试策略，以便总线质量差的时候不必整体重来。
4. 作为刷写工程师，我想要关键步骤（擦除、传输中）标记为不可取消，以免误点一下让 ECU 停在半擦除状态。
5. 作为刷写工程师，我想要非关键步骤可以取消，以便发现刷错文件时能及时停手。
6. 作为刷写工程师，我想要刷写过程中持续看到「当前第几步、已传输多少字节、总共多少」，以便判断是否要继续等。
7. 作为刷写工程师，我想要进度通过事件推送而不是直接写界面，以便同一套逻辑既能喂 CLI 又能喂将来的桌面界面。
8. 作为刷写工程师，我想要断连后重跑能从上次完成的段继续，以便十几分钟的工作不被一次抖动毁掉。
9. 作为刷写工程师，我想要续刷前校验「镜像没换、配方没换、目标没换」，以免从半截接着刷出一个既不是旧版也不是新版的 ECU。
10. 作为刷写工程师，我想要续刷校验不通过时明确报错并拒绝执行，而不是默默从头刷或默默继续。
11. 作为刷写工程师，我想要擦除步骤被记录在检查点里，以便续刷时不会重复擦写已经擦好的段。
12. 作为刷写工程师，我想要检查点只包含「已完成到哪」而不包含待传数据，以免把几十 MB 镜像复制进状态文件。
13. 作为质量工程师，我想要每次刷写都留下一条审计记录（时间、操作者、目标、文件指纹、结果），以便体系审核时能回答。
14. 作为质量工程师，我想要审计记录长期留存、不被日志轮转清理，以便三个月后还能查到。
15. 作为质量工程师，我想要失败的刷写也留痕（而不是只记录成功的），以便定位「这台 ECU 是不是被反复刷失败过」。
16. 作为质量工程师，我想要审计记录能按目标 ECU 与文件指纹检索，以便回答「这个版本刷过哪些台」。
17. 作为架构负责人，我想要网关接口只传字节与字典，以便将来实现搬到独立进程、或用 C++/Rust 重写时不改动上层。
18. 作为架构负责人，我想要刷写逻辑一行都不依赖具体总线（CAN / DoIP / 仿真），以便新增通道只是加一个插件。
19. 作为架构负责人，我想要 UDS 这类协议专有细节留在插件里，以便领域核心保持干净、不被具体协议名污染。
20. 作为开发者，我想要在没有 CAN 卡、没有 ECU 的笔记本上跑通整套刷写流程的测试，以便开发不依赖台架。
21. 作为开发者，我想要仿真网关能脚本化「第 N 次请求返回什么」，以便精确复现超时、否定响应、中途断连这些异常路径。
22. 作为开发者，我想要配方状态机是纯数据 + 纯函数，以便单测不需要任何 IO。
23. 作为开发者，我想要所有异常路径都有显式断言（而不是「没抛异常就算过」），以免又踩「不报错只是安静地错」那类坑。
24. 作为使用者，我想要在命令行里发起一次刷写并看到逐步进度，以便没有桌面界面时也能用。
25. 作为使用者，我想要命令行能显示「上一次刷写到哪断了、能不能续」，以便决定要不要重跑。
26. 作为使用者，我想要命令行能列出历史刷写记录，以便查「上次刷这个 ECU 是什么时候」。
27. 作为使用者，我想要刷写失败时看到具体的步骤与原因（哪一步、什么响应、重试了几次），以便判断是接线问题还是文件问题。
28. 作为使用者，我想要否定响应（NRC）被翻译成人能读的话，以便不用抱着 ISO 14229 手册查 0x7F 0xXX。
29. 作为使用者，我想要安全访问失败有明确提示，以便区分「密钥错了」和「还没请求种子」。
30. 作为使用者，我想要刷写完成后自动校验（校验和 / 回读比对），以便刷完就能确认成功而不是等到上车才发现。
31. 作为使用者，我想要刷写完成后能复位 ECU 并确认它活着，以便知道这次刷写真的生效了。
32. 作为维护者，我想要新增一个配方插件不需要改动内核任何一行代码，以便迭代成本可控。
33. 作为维护者，我想要新增的插件在依赖契约里被登记，以便强迫自己思考「这真的是一个独立插件吗」。
34. 作为维护者，我想要刷写相关的领域模型集中在独立目录里，以便它与标定、测量互不感知、各自演进。
35. 作为使用者，我想要刷写用的镜像复用标定域已建好的地址空间模型，以便「按段写进 ECU」这件事不用重新造一套数据结构。

## Implementation Decisions

### 唯一的测试缝：网关字节边界

整套刷写逻辑只在一个地方与外界接触：**配方产出一串请求字节，网关返回一串响应字节**。所有测试都在这个缝上做——用一个脚本化的仿真网关替代真实硬件。

这是刻意的选择：真实 CAN 卡、真实 ECU 在开发环境里不存在，而刷写逻辑的复杂度（时序、重试、断点续刷、审计）与「字节怎么上总线」完全无关。把它们绑在一起测试会让测试又慢又脆，而且逻辑错误会被硬件噪声掩盖。

### 配方（Recipe）是新扩展点，且只增不改

`core/ports` 里已有的 `Gateway` 协议保持不变。新增一个 `Recipe` 协议（此前只有能力枚举、没有协议），配方插件实现它。

**扩展点只增不改**：不去给 `Gateway` 加方法（那会让已有插件全部失效），而是新增一个协议。

### 协议专有细节一律下沉到插件

领域核心里不允许出现 UDS / CAN / DoIP 这类名字。因此：

- 核心只定义**语义步骤**（进入编程会话、安全访问、擦除、传输、校验、复位）与它们的数据形状；
- 把这些步骤翻译成具体协议字节的工作，由配方插件完成；
- 网关插件只负责「送字节、收字节」，不解释协议含义。

这样将来支持非 UDS 的 Bootloader 时，只是再加一个配方插件。

### 领域模型：刷写域自有，不合并进别的域

在 `core/models` 下新建刷写域模型，包含六类实体：目标（ECU 标识、诊断地址、内存布局）、步骤类型、步骤（含超时、重试、是否可取消）、配方（有序步骤 + 前置条件）、进度（当前步、已完成段、已传输字节）、审计记录（时间、操作者、目标、文件指纹、结果）。

它们与标定域、测量域**互不感知**。唯一共享的是已建好的地址空间模型——因为「把镜像按段写进 ECU」与标定域用的是同一个概念，这是自然内聚，不是强行统一。

### 断点续刷：检查点在段边界，且恢复前必须校验

- 检查点只在**段边界**落盘，记录：已完成到第几段、配方指纹、镜像指纹、目标标识、擦除是否已做。
- 恢复前逐项校验这四项。**任何一项不一致就拒绝续刷并明确报错**——从半截接着刷出一个「既不是旧版也不是新版」的 ECU，是这类系统里后果最严重的静默错误。
- 检查点不含镜像数据本身，只含指纹与游标。
- 擦除状态记在检查点里：已经擦过的段不重复擦（重复擦写既慢又损耗 Flash）。

### 作业参数：可续、且关键步骤不可取消

刷写作业声明为**可续**（失败后支持续跑，而非重跑）；**步骤级**声明是否可取消——擦除与传输中不可取消，其余可取消。

取消保护是分层的：作业级允许取消请求进来，但落到不可取消的步骤上时，取消被推迟到该步骤结束，而不是中途中断让 ECU 停在半擦除状态。

### 审计记录：追加写、长期留存、失败也记

- 一次刷写作业一条记录，追加写入独立文件（JSONL，一行一条）。
- 刻意不用带表头的表格格式：表头一旦改字段，错位会让整行数据静默错列。
- 成功与失败都要记，失败记录里带步骤摘要与错误原因。
- 记录内容包含：开始与结束时间（UTC）、操作者、目标标识、镜像指纹、配方标识、结果、耗时。

### 进程边界：契约先到位，真进程后置

接口签名只传 `bytes` 与 `dict`，不含对象引用或回调——这是「将来能搬到独立进程 / 用 C++ 重写」的前提条件，现在就把这个约束钉死。

P3 阶段落地进程内实现；真正把网关搬到独立进程、走本地管道，放在后续阶段。因为接口已经是可序列化的，届时替换传输层不需要改动任何上层逻辑。

### 依赖方向不变

新增代码严格遵守 `apps → services → platform → core ← plugins`：领域模型进 `core/models`，审计文件写入进 `platform`，用例编排进 `services`，配方与网关是插件。新增的插件在依赖契约里登记。

## Testing Decisions

### 什么算好测试

- **只测外部行为，不测实现细节。** 断言「给定这串响应字节，刷写走到了第几步、进度是多少、审计记了什么」，不断言内部调用了哪个私有函数。
- **期望值来自独立事实源**，不是照着实现算一遍。步骤序列、字节数、检查点内容都应是能对照手册核对的字面量。
- **必须断言「值对」，不能只断言「没抛异常」。** 这是本项目反复强调的一条：不报错只是安静地错，是这里最危险的一类缺陷。
- **异常路径与正常路径同等重要。** 超时、否定响应、中途断连、续刷校验不通过，都要有对应断言。

### 在哪里测

全部在**网关字节边界**这一个缝上，用仿真网关驱动。具体覆盖：

1. **配方状态机**：步骤按顺序推进；步骤参数（超时、重试、可取消）被正确解释；纯数据、纯函数、无 IO。
2. **刷写编排**：正常跑完产生正确的进度序列与审计记录；每个阶段的进度数值可核对。
3. **断点续刷**：在指定段中断后，续跑从该段继续——**断言擦除步骤没有被重复执行**；镜像/配方/目标任一变化即拒绝续刷。
4. **取消保护**：不可取消步骤期间收到取消请求不被中断（在该步骤结束后停止）；可取消步骤能及时停。
5. **审计**：成功与失败都有记录；记录字段值正确（不是「写了文件就行」）。
6. **契约与纪律**：沿用已有的分层测试与依赖方向契约；新增插件登记后契约仍然全绿。

### 参照既有做法

沿用仓库已有的测试风格：样例数据可复现（生成器脚本）、断言逐项核对而非快照、分层纪律由 AST 扫描与依赖契约执行。仿真网关的脚本化响应方式，参照 BLF 测试里已有的「自带最小写入器造边界样本」的做法。

## Out of Scope

- **真实硬件驱动**。不做 Vector / PeakCAN / Kvaser 等具体 CAN 卡的驱动实现，只留好网关插件位。真机上联调需要在有设备的环境下另做。
- **真实 DoIP / ISO-TP 传输实现**。P3 只保证接口能承载它们，不实现 ISO-TP 分包重组与 DoIP 路由激活的完整状态机。
- **独立进程与本地管道**。接口已按可序列化设计，但 P3 不落地子进程管理与跨进程传输。
- **桌面界面**。P3 只有命令行入口；桌面壳属于后续阶段。
- **安全访问算法本身**。配方声明「需要安全访问」与种子密钥的交换顺序，具体算法（各家私有）由配方插件自带，不进核心。
- **CDM 写回**（改动标定后生成新的 HEX / S19）。那是标定域的待办，与刷写域正交。
- **并发刷写多台 ECU**。P3 一次只处理一个目标。
- **刷写文件的解析**。镜像以已建好的地址空间模型传入，解析由既有解析器负责。

## Further Notes

1. **不可重放是这一域与前三期的本质差异。** 标定比对错了可以重跑，刷写错了是物理事故。因此本域里凡是「不确定就继续」的地方，默认值必须是**停下来报错**。
2. **配方指纹必须包含配方内容与顺序**。只比对配方名会漏掉「改了步骤顺序但没改名」的情况。
3. **镜像指纹用内容哈希**，与项目既有的工件指纹做法一致（换文件名不影响命中）。
4. **进度汇报要能去重**：相同的进度不重复发事件，否则高频传输会刷爆事件总线。已有骨架支持这一点。
5. **审计时间统一 UTC**，避免夏令时与时区导致的排序错乱；展示层再转本地时间。
6. **否定响应的翻译表放在插件里**（它属于协议专有知识），核心只传递「步骤失败 + 原始响应字节」。
7. 后续若要接真实硬件，第一步是加一个网关插件 + 一个真机配方，领域模型与编排层不需要改动。
